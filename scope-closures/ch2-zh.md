## 大理石,还有巴基特,还有泡泡... 天呐!

我发现在理解范围方面有效的一个比喻是 将彩色大理石分拣成 其匹配颜色的桶。

想象一下你会遇到一堆大理石, 并且注意到所有的大理石都是红色,蓝色或绿色的。 把大理石都整理一下,把红的扔进红桶,绿的扔进绿桶,蓝的扔进蓝桶. 排序后,当你以后需要绿色的大理石时,你已经知道绿色的桶是去得到它的地方.

在这个比喻中,大理石是我们程序中的变量. 这些桶是瞄准镜(功能和块),我们只是从概念上为讨论目的指定了个别颜色。 每块大理石的颜色由此决定,我们从哪个*color* 范围中找到最初创建的大理石.

让我们从第1章中标注运行中的程序示例,并标注范围颜色标签:

```js
// outer/global scope: RED

var students = [
    { id: 14, name: "Kyle" },
    { id: 73, name: "Suzy" },
    { id: 112, name: "Frank" },
    { id: 6, name: "Sarah" }
];

function getStudentName(studentID) {
    // function scope: BLUE

    for (let student of students) {
        // loop scope: GREEN

        if (student.id == studentID) {
            return student.name;
        }
    }
}

var nextStudent = getStudentName(73);
console.log(nextStudent);   // Suzy
```

我们指定了三种带有代码注释的视野颜色:RED(全球范围以外),BLUE(功能范围)`getStudentName(..)`和GREEN(范围/范围)`for`(原始内容存档于2017-03-26). loop. 但是,在查看一个代码列表时,可能仍然难以识别这些瞄准桶的边界.

当JS引擎处理一个程序(在编译过程中),并找到一个变量的宣告时,它基本上问道,“我目前处在哪个*color*范围(泡泡或桶子)?” 该变量被指定为同一个*color*,表示它属于那个桶/泡.

GREEN(3)桶完全嵌入BLUE(2)桶内,同样BLUE(2)桶完全嵌入RED(1)桶内. 范围可以像显示的那样在彼此内部筑巢,按照程序需要达到任何深度的筑巢.

如果在目前范围内有匹配声明,或者在目前范围内之上/之外有任何范围,则允许提及变量/识别符(非声明),但不允许与较低/取消范围的声明相匹配。

RED(1)水桶中的一种表达方式只能使用RED(1)大理石,**不**BLUE(2)或GREEN(3). BLUE(2)桶中的一种表达方式可以参考BLUE(2)或RED(1)大理石,**不**GREEN(3). 而GREEN(3)桶中的一种表达方式可以访问RED(1),BLUE(2),以及GREEN(3)大理石.

我们可以构思如何确定这些未声明的大理石颜色, 自从`students`变量引用`for`-9号线的Loop语句不是声明,没有颜色. 因此,我们询问目前的BLUE(2)瞄准镜桶是否有与这个名字匹配的大理石. 由于它没有,因此继续以下一个外/含范围:RED(1). RED(1)桶有一个大理石的名字`students`,所以循环声明的`students`可变参照被确定为RED(1)大理石.

那个`if (student.id == studentID)`10号线的语句同样决心提及GREEN(3)大理石`student`和一个BLUE(2)大理石`studentID`.

## 朋友之间的对话

分析变量的过程和它们来自的范围的另一个有用的比喻是想象在代码处理后执行时在引擎内部发生的各种对话. 我们可以"倾听"这些对话,为范围如何工作获得更好的概念基础.

现在请见JS引擎的成员,

* *Engine*:负责我们的JavaScript程序的开始到完成编译和执行.

* *编译者*:*Engine*的朋友之一;处理解析和代码生成的所有肮脏工作(见上一节).

* *Scope Manager *: *Engine *的另一个朋友;收集并维护所有已宣布的变量/识别符的查询列表,并强制执行一套规则,说明这些变量/识别符如何可供当前执行代码使用.

要让你完全理解 JavaScript 是如何工作的,你需要开始思考 喜欢 * Engine * (和朋友) 思考,问他们问的问题,并同样回答他们的问题.

为了探索这些对话,我们再次回顾我们运行的程序实例:

```js
var students = [
    { id: 14, name: "Kyle" },
    { id: 73, name: "Suzy" },
    { id: 112, name: "Frank" },
    { id: 6, name: "Sarah" }
];

function getStudentName(studentID) {
    for (let student of students) {
        if (student.id == studentID) {
            return student.name;
        }
    }
}

var nextStudent = getStudentName(73);

console.log(nextStudent);
// Suzy
```

让我们来检查JS将如何处理这个计划, 特别是从第一个声明开始。 该阵列及其内容只是联署材料的基本价值(因此不受任何范围界定关切的影响),因此,我们这里的重点是:`var students = [ .. ]`申报和初始化-分配部分。

我们通常把这看作是一个单一的说法,但这不是我们的朋友*Engine*如何看待的. 事实上,联署材料将这些行动视为两种不同的行动,一种是汇编过程中处理,另一种是执行过程中处理。

与这个程序相关的第一件事 * 编译器 * 将执行 Lexing 来将其细分为符号,然后将其分解为树( AST)。

一旦* 编译器* 得到代码生成, 有更多的细节需要考虑 比可能很明显。 一个合理的假设是,*编译器*将为第一个语句产生代码,例如:"一个变量的Allocate内存,标注它.`students`,然后在变量中加入一个引用数组的符号。” 但这不是整个故事。

接下来是《编译者》 处理这个声明的步骤:

1. 面对`var students`, * 编译器 * 将要求 * 范围管理器 * 查看一个变量是否命名`students`已经存在这个特殊的瞄准筒。 如果是这样,* 汇编者* 会无视这一宣言,继续前进。 否则, * 编译器 * 将生成代码( 执行时), 要求 * 范围管理器 * 创建一个新的变量`students`在瞄准镜桶。

2. * 编译器 * 然后为 * Engine * 生成代码, 用于以后执行, 处理`students = []`任务。 代码 * Engine * 运行时会先询问 * 范围管理器 * 如果有一个变量叫做`students`可进入当前瞄准镜桶。 如果不是,则*Engine*继续寻找别处(见下文"Nested Specification"). 一旦 * Engine * 找到变量,它就会指定引用`[ .. ]`数组到它。

在对话形式上,程序编译的第一阶段可能会在 * 编译器 * 和 * 范围管理器 * 之间展开这样的游戏:

> *** 编译器***:嘿,* 范围管理器 * (全球范围),我找到一个正式声明,要求识别符名为`students`听说过吗?

> ***(全球)范围管理器***: 没有,从来没有听说过它, 所以我刚刚创造了它给你。

> *** 编译器***:嘿,* 范围管理器 *,我找到一个正式的申报,一个标识符叫做`getStudentName`听说过吗?

> ***(全球)范围管理器***: 没有,但我刚为你创造了它。

> *** 编译器***: 嘿, * 范围管理器 *,`getStudentName`指出一个函数,所以我们需要一个新的瞄准筒。

> ***(功能)范围管理器***: 明白,这里是瞄准镜桶

> *** 编译器***: 嘿, * 范围管理器 * (功能), 我找到一个正式的参数声明, 用于`studentID`听说过吗?

> ***(功能)范围管理器***: 没有,但现在它是在这个范围。

> *** 编译器***: 嘿, * 范围管理器 * (功能),我发现了一个`for`- 需要自己的瞄准镜桶

> ...

对话是一种问答交换,其中 ** 编译器 ** 询问当前 * 范围管理器 * 是否已经遇到遇到的标识声明。 如果"否", *范围管理器 * 创建了该范围的变量. 如果答案是"是",那么它实际上被跳过,因为没有其他可以做的*范围管理员*.

*编译器*在跨函数或块瞄准镜运行时也发出信号,这样新的瞄准镜桶和*范围管理器*就可以被即时化.

后来,在程序执行方面,对话会转移到*Engine*和*Scope Manager*,并可能这样演奏:

> *** Engine ***: 嘿, * 范围管理器 * (全球范围), 在我们开始之前, 你能查一下标识符吗?`getStudentName`这样我就可以把这个功能分配给它?

> ***(全球)范围管理器***: 是的,这里的变量。

> *** 发动机 ***: 嘿,"范围经理",我找到一个"目标"参考`students`听说过吗?

> ***(全球)范围管理器***: 是的,这是正式宣布的,所以在这里。

> *** 发动机 ***: 谢谢,我刚开始`students`改为:`undefined`,所以它准备使用。

> 嘿,*范围管理员 * (全球范围),我找到一个*目标*参考`nextStudent`听说过吗?

> ***(全球)范围管理器***: 是的,这是正式宣布的,所以在这里。

> *** 发动机 ***: 谢谢,我刚开始`nextStudent`改为:`undefined`,所以它准备使用。

> 嘿, * 范围管理器 * (全球范围), 我找到了一个 * source * reference for`getStudentName`听说过吗?

> ***(全球)范围管理器***: 是的,正式宣布了这一范围。 在这里。

> *** 发动机 ***: 不错, 值在`getStudentName`是一个功能, 所以我要执行它。

> *** Engine***: 嘿, * 范围管理器 *, 现在我们需要即时化函数的范围。

> ...

此对话是另一个问答交流, 其中 * Engine * 首次要求当前 *Scope 管理器 * 向上查看升起的`getStudentName`标识符,以便将该函数与其关联。 * Engine * 然后询问“范围管理器”有关“目标”的参考文献。`students`,还有其他的

审查和总结说明如何`var students = [ .. ]`分两个不同步骤处理:

1. *编译器 *设置了范围变量的申报(因为以前没有在目前范围中申报).

2. * Engine * 正在执行时, 为了处理语句中的任务部分, * Engine * 要求 * Scope 管理器 * 查看变量, 初始化为`undefined`因此,它已经准备好使用,然后为它分配数组值.

## 嵌入范围

当是时候执行`getStudentName()`函数, *Engine * 请求为该函数的范围设置一个 * 范围管理器 *, 然后它会继续查找参数(`studentID`指定`73`参数值,等等。

函数范围`getStudentName(..)`位于全球范围内。 块范围`for`-Loop也同样被嵌入到这个功能范围内。 范围可以按照程序定义,在任意的深度上依逻辑嵌入.

每个范围每次执行范围(一次或多次)都会得到自己的*范围管理器*实例. 每个范围都会在被执行范围开始时自动登记其所有标识符(这被称为"可变悬浮";参见第五章).

在范围开始时,如果有任何识别资料来自`function`,该变量将自动初始化到其相关函数引用。 如果有任何识别资料来自`var`声明(相对于`let`/`const`),该变量自动初始化为`undefined`这样它就可以被使用;否则,变量仍然未初始化(aka,在其"TDZ"中,参见第5章),在完全声明和初始化执行之前不能使用.

在那个`for (let student of students) {`声明,`students`是一个必须查阅的 * 来源 * 引用。 但是,如何处理这种检查,因为功能的范围不会找到这样的标识符?

解释一下,让我们想象一下 那种对话是这样玩的:

> *** Engine ***: 嘿, * 范围管理器 * (用于函数), 我有一个 * source * reference for`students`听说过吗?

> ***(功能)范围管理器***: 没有,从来没有听说过。 试下一外观.

> *** Engine ***: 嘿, * 范围管理器 * (全球范围), 我有 * 来源 * 参考文献`students`听说过吗?

> ***(全球)范围管理器***: 是的,这是正式宣布的,在这里。

> ...

词典范围的一个关键方面是,任何在目前范围中无法找到标识参考物,都要咨询巢穴中下一个外部范围;在找到答案或没有更多的范围可供咨询之前,要重复这一过程.

### 搜索失败

当 * Engine * 耗尽所有 * 语法可用的 * 范围( 向外移动), 并且仍然无法解决身份识别符的查找时, 则存在一个错误条件。 然而,取决于程序模式(是否严格模式)和变量的作用(即*目标*对*源*;参见第一章),这个错误条件会得到不同的处理.

#### 未定义的 Mess

如果变量是 * source *, 未解决的标识符查询则被视为未宣布的(未知的,缺失的)变量,这总是导致`ReferenceError`被丢弃。 此外,如果变量是一个*目标*,而此时的代码在严格模式下运行,则该变量被视为未宣布,并同样投掷一个`ReferenceError`.

在大多数JS环境中,一个未宣布的可变条件的错误消息会看起来像"参考错误:XYZ没有定义". "未定义"这一短语与"未定义"一词似乎几乎相同,就英语而言. 但两者在JS中差异很大,这一错误信息不幸造成了持续的混乱.

"未定义"其实是"未宣布"的意思,或者说,"未宣布"的意思,就像一个在任何 * 语法上可用的* 范围内没有匹配的正式声明的变量. 相比之下,"未定义"确实意味着一个变量被找到(声明),但该变量在当时没有其他值,因此默认为`undefined`数值。

进一步延长混乱,联署材料`typeof`操作员返回字符串`"undefined"`用于两种状态中的变量引用:

```js
var studentName;
typeof studentName;     // "undefined"

typeof doesntExist;     // "undefined"
```

这两种可变的提法在条件上大不相同,但JS确实将水弄脏了. 术语混乱令人困惑,非常不幸。 不幸的是,JS开发者只需密切关注,不要把"他们正在处理的"哪一种"混为一谈!

#### 全球... 你说什么?

如果变量是一个*目标*,严格模式并没有生效,那么一个令人困惑和令人惊讶的遗留行为就会被触发. 麻烦的结果是,全球范围的“范围管理者”将仅仅创建一个**偶然的全球变量** 来完成目标任务!

考虑:

```js
function getStudentName() {
    // assignment to an undeclared variable :(
    nextStudent = "Suzy";
}

getStudentName();

console.log(nextStudent);
// "Suzy" -- oops, an accidental-global variable!
```

接下来的“对话”将如何进行:

> *** Engine ***: 嘿, * 范围管理器 * (为函数), 我有一个“ 目标” 参考`nextStudent`听说过吗?

> ***(功能)范围管理器***: 没有,从来没有听说过。 试下一外观.

> *** Engine***: 嘿, * 范围管理器 * (全球范围),我有一个* 目标* 参考:`nextStudent`听说过吗?

> ***(全球)范围管理器***: 不,但既然我们在非限制模式, 我帮助你 并刚刚为你创造了一个全球变量, 在这里!

恶心。

这种事故(几乎可以肯定最终导致bugs)是严格模式提供有益保护的伟大例子,为什么如此糟糕的想法*不*使用严格模式. 严格来说,

> ***(全球)范围管理器***: 没有,从来没有听说过。 对不起,我得扔一个`ReferenceError`.

分配到一个从未宣布的变量 * 是一个错误,所以我们收到一个`ReferenceError`在这里。

永远不要依赖意外的全球变量。 总是使用严格的模式,并且总是正式宣布你的变量. 你就会得到一个帮助`ReferenceError`如果你曾经错误地试图指定 一个未声明的变量。

这栋建筑代表了我们节目的巢形瞄准镜收藏. 大楼一楼是目前的执行范围。 该建筑的顶层是全球范围.

解决一个*目标*或*源*可变的参考,首先在目前的地板上查看,如果找不到,就搭电梯到下一层(即一个外延),再看那里,然后是下一个,等等. 一旦到达顶层(全球范围),要么找到自己要找的东西,要么就找不到. 但你必须停止不管。

## 继续对话

到此为止,你应该开发更丰富的心理模型,说明什么是范围,JS引擎如何从你的代码中决定和使用它.

在 * 继续 * 之前, 在您的一个项目中找到一些代码, 并运行这些对话。 说真的,实际上大声说出来。 找个朋友 和他们一起练习每个角色 如果你们中谁发现自己困惑或绊倒了 花更多的时间审查这些材料
