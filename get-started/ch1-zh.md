## 叫什么来着?

JavaScript这个名字可能是最错误和误解的编程语言名称.

这个语言和Java有关吗? 是不是只有Java的脚本形式? 它是否只用于编写脚本而不是真正的程序?

真相是,JavaScript这个名字是市场营销的艺术品. 当布伦丹·艾希第一次构思该语言时,他代号为"莫查". 在Netscape内部,使用了LiveScript这个品牌. 但到了公开命名语言的时候,"JavaScript"赢得了投票.

为什么? 因为这种语言最初是为了吸引大多数Java程序员的观众,也因为"script"一词在当时很流行,用来指轻量级程序. 这些轻量级的"标语"将会是最早嵌入这个名为网络的新事物的页面的!

换句话说,JavaScript是一个营销伎俩,试图将这种语言定位为一种优美的替代语言,而不是写出更重,更著名的当日的Java. 它可能同样容易 被叫做"WebJava" 这件事情。

JavaScript的代码和Java代码之间有一些表面的相似之处. 这些相似性并不特别来自于共享开发,而是来自两种语言针对的开发者,其设定的语法期望来自C(以及在一定程度上来自C++).

例如,我们使用`{`开始一组代码和`}`像C/C++和Java一样 结束那块代码 我们也使用`;`以插入语句的结尾。

在某些方面,法律关系比语法更深入. Oracle(通过Sun),仍然拥有和运营Java的公司,也拥有名为"JavaScript"的官方商标(通过Netscape). 这个商标几乎从未被执行过,此时很可能不可能.

出于这些原因,有些人建议我们使用JS而不是JavaScript. 这是一个非常普通的简称,如果不是正式语言品牌的好候选人的话。 实际上,这些书几乎完全使用JS语言。

进一步将语言与甲骨文拥有的商标隔开,TC39指定并由ECMA标准机构正式确定的语言的正式名称是**ECMAScript**. 而实际上,自2016年起,官方语言名称也被修订年所后缀;从此写法,即ECMAScript 2019,或简称ES2019.

换句话说,在您的浏览器或Node.js运行的JavaScript/JS是**执行ES2019标准.

JS的语法和行为在ES规格中定义.

ES2019恰好是自1995年JS成立以来的第10大编号规格/修订版,所以在ECMA主机的规格官方URL中,你会发现"10.

TC39委员会由50至100名不同人士组成,他们来自网页投资的公司,如浏览器制造商(Mozilla,Google,Apple)和设备制造商(Samsung等)。 委员会的所有成员都是志愿者,尽管其中许多是这些公司的雇员,因此他们可能因在委员会中的职责而得到部分补偿。

### 网络规则( JS)

管理JS的环境范围在不断扩展(从浏览器,到服务器(Node.js),到机器人,到灯泡,到.),而管理JS的唯一环境是网络。 换句话说,在网络浏览器上如何实施JS,在所有实际中,都是唯一重要的现实.

在大部分情况下,在规格中界定的JS和在基于浏览器的JS引擎中运行的JS是相同的. 但有一些分歧必须加以考虑。

有时JS规格会规定一些新的或精细的行为,然而这与基于浏览器的JS引擎的运作方式并不完全吻合. 这种不匹配是历史性的:JS引擎在网络内容所依赖的功能的角落案例周围有20多年的可观察到的行为. 因此,联署材料的引擎有时会拒绝遵守专门规定的更改,因为它会打破网页内容。

## 许多面孔

编程语言语境中的"paradigm"一词是指一种广泛的(几乎通用的)思维模式和构建代码的方法. 在范式中,风格和形式有各种各样的差异来区分程序,包括无数不同的图书库和框架,这些图书库和框架在任何给定的代码上留下其独特的签名.

但是,不管一个程序的个人风格是怎样的,关于范式的大图解几乎总是在任何程序的第一眼中显而易见的.

典型的范式级编码类别包括程序、面向对象(OO/类)和功能(FP):

* 程序风格通过预先确定的一组操作组织自上而下,线性进化的代码,通常在称为程序的相关单元中一起收集.

* OO风格通过收集逻辑和数据将代码组织为称为类的单位.

* FP风格将代码组织为函数(纯粹的计算而不是程序),并将这些函数作为值的调整.

譬喻无对无错. 它们是引导和塑造程序员如何处理问题和解决方案,如何构建和维护其代码的方向.

有些语言严重倾向于一种模式——C是程序性的,Java/C++几乎完全面向阶级,Haskell是FP通过和通过。

但许多语言也支持可以来自不同范式的代码模式,甚至混合和匹配. 因此,所谓的"多种paradigm语言"提供了最终的灵活性. 在某些情况下,一个单一的程序甚至可以有两个或两个以上的这些范式的表达方式并排而坐.

JavaScript是最肯定的多参数语言. 你可以写程序,面向班级,或FP式的代码,你可以逐行做出这些决定,而不是被迫做出一个全或全无的选择.

## 向后移动( F)

指导JavaScript的最基本原理之一是维护*背面兼容性*. 许多人被这个术语的意义所混淆,并经常将其与一个相关但不同的术语混淆:*向前的兼容性*.

举正录.

反向兼容性意味着,一旦某物被接受为有效的JS,将来不会改变导致该代码成为无效JS的语言. 1995年写的代码,无论多么原始或有限,今天仍应有效。 正如TC39成员经常宣称的那样,"我们不打破网络!"

想法是JS开发者可以自信地写出代码,因为他们的代码不会因为浏览器更新发布而无法预测地停止工作. 这使得选择联合机构参与一项方案的决定成为今后更明智和安全的投资。

"担保"不是小事 在语言历史的近25年中保持反向兼容性,造成了巨大的负担和一系列独特的挑战。 在计算这种向后兼容性的承诺时,你很难找到许多其他例子。

坚持这一原则的代价不应随意放弃。 它必然为包括修改或扩展语言设置了一个非常高的屏障;任何决定实际上都是永久的、错误的和所有的。 一旦在JS中,它不能被取出来,因为它可能打破程序,即使我们真的,真的想把它删除!

这一规则有一些小的例外。 联合来文有一些向后不相容的变化,但TC39对此极为谨慎。 他们研究网络上现有的代码(通过浏览器数据收集)来估计这种断开的影响,浏览器最终决定和表决他们是否愿意接受用户的热量来进行非常小的断开,权衡了为更多网站(和用户)修补或改进语言某些方面的好处.

这些变化是罕见的,而且几乎总是出现在许多网站不太可能明显破裂的角落使用中。

比较 * backwards 兼容性* 与其对应方, *forwards 兼容性*. 与前置兼容意味着,在程序中添加新的语言,如果程序运行在更老的JS引擎中,不会导致程序破裂. ** 尽管许多人都希望这样做,但JS并不与前行相容**,甚至错误地相信了它的神话。

相比之下,HTML和CSS是前向兼容的,但不是后向兼容的. 如果你在1995年挖出一些HTML或CSS回写,那么在今天完全有可能是行不通的(或者同样的工作). 但是,如果在从2010年开始的浏览器中使用2019年的新功能,页面不是"断开"——未识别的CSS/HTML被跳过,而其余的CSS/HTML则会被相应处理.

在编程语言设计中包含远期兼容性可能显得可取,但这样做一般是不切实际的. Markup(HTML)或stypling(CSS)在性质上是宣示性的,因此"滑过"未确认的声明会更容易,对其他公认的声明影响最小.

但是,如果一个编程语言引擎有选择地跳过声明(甚至表达式!),而它不理解的话,就会出现混乱和非决定性,因为无法确保程序之后的部分不会期望跳过的部分得到处理.

虽然JS不是,而且不可能是前向兼容的,但必须承认JS的后向兼容性,包括它给网络带来的持久好处以及由此给JS带来的限制和困难.

### 跳跃空白

由于JS不与前置兼容,这意味着在您可以写出有效JS的代码与您的网站或应用程序需要支持的最古老的引擎之间总是存在着漏洞. 如果运行一个从2016年开始在引擎中使用ES2019特性的程序,则非常有可能看到程序中断和崩溃.

如果特性是新的语法,程序一般会完全无法编译和运行,通常会扔出一个语法错误. 如果特性是 API(例如 ES6's)`Object.is(..)`),该程序可能运行到一个点,但随后丢出运行时的例外,一旦遇到未知的API的引用就停止.

这是否意味着JS开发者应该总是落后于进步步伐,只使用处于他们需要支持的最古老JS引擎环境后边缘的代码? 没有!

但这确实意味着JS开发者需要特别注意解决这一缺口.

对于新的和不相容的语法,解决方案是转写. Transpiling是一个由社区发明的术语,用来描述使用一种工具将程序的源代码从一种形式转换到另一种形式(但仍作为文本源代码). 通常情况下,与语法相关的前置兼容性问题通过使用转写器(最常见的是Babel(https://babeljs.io),从较新的JS语法版本转换为等效的旧语法.

例如,开发者可能会写出一个代码片段,例如:

```js
if (something) {
    let x = 3;
    console.log(x);
}
else {
    let x = 4;
    console.log(x);
}
```

用于该应用程序的代码在源代码树上是这样看的. 但当制作文件部署到公共网站时, Babel 转写器可能会将代码转换成这样:

```js
var x$0, x$1;
if (something) {
    x$0 = 3;
    console.log(x$0);
}
else {
    x$1 = 4;
    console.log(x$1);
}
```

原始片段依赖`let`以创建块范围`x`两个变量`if`和`else`条款互不干扰。 Babel可以制作的等效程序(使用最小的复工)只是选择用独特的名称来命名两个不同的变量,产生相同的不干涉结果.

| 注: |
| :--- |
| 那个`let`ES6中增加了关键词(2015年). 以上转录的例子只有在申请需要在支持联合来文的ES6前环境中运行的情况下才能适用。 这里的例子只是为了简单说明。 当ES6是新的时,这种转录的需要相当普遍,但在2020年,支持ES6前期环境的需要就少得多了. 因此,用于转录的"目标"是一个滑动窗口,它只在决定一个网站/应用程序停止支持一些旧的浏览器/引擎时向上移动. |

你可能会问:为什么用一个工具来从较新的语法版本转换成较旧版本? 我们不能只写两个变量 然后跳过`let`关键词? 原因是,强烈建议开发者使用JS的最新版本,使其代码干净,并最有效地传达其思想.

开发者应注重写清新语法表格,让工具注意制作一个适用于部署和运行最古老的JS引擎环境的与前向兼容的代码版本.

### 填补空白

如果远期兼容性问题与新语法无关,而是与最近才添加的缺失API方法有关,那么最常见的解决方案就是为缺失的API方法提供定义,该方法的存在和行为仿佛旧环境已经有本土定义. 这种图案被称为多填充(aka "shim").

考虑这个代码:

```js
// getSomeRecords() returns us a promise for some
// data it will fetch
var pr = getSomeRecords();

// show the UI spinner while we get the data
startSpinner();

pr
.then(renderRecords)   // render if successful
.catch(showError)      // show an error if not
.finally(hideSpinner)  // always hide the spinner
```

此代码使用 ES2019 特性,即`finally(..)`在承诺的原型。 如果在ES2019前环境中使用此代码,则`finally(..)`方法不存在,并会出现错误。

组合填充`finally(..)`在ES2019前的环境下,可以看起来像这样:

```js
if (!Promise.prototype.finally) {
    Promise.prototype.finally = function f(fn){
        return this.then(
            function t(v){
                return Promise.resolve( fn() )
                    .then(function t(){
                        return v;
                    });
            },
            function c(e){
                return Promise.resolve( fn() )
                    .then(function t(){
                        throw e;
                    });
            }
        );
    };
}
```

| 警报: |
| :--- |
| 这只是一个简单的例子,说明基本(不完全符合规格)的多填充。`finally(..)`。不要在代码中使用这种多填充;只要可能,总是使用坚固的,正式的多填充,如ES-Shim中收集多填充/吸附. |

那个`if`语句保护多填充定义,防止其在JS引擎已经定义过该方法的任何环境中运行. 在较旧的环境中,多填充被定义,但在较新的环境中,`if`语句被悄悄跳过。

Babel 等 Transpillers 通常检测您的代码需要的多填充并自动为您提供. 但偶尔你可能需要包括/明确定义它们, 它的工作类似于我们刚刚看到的片段。

总是使用最合适的特性来写代码,以有效地传达其思想和意图. 一般而言,这意味着使用最新稳定的联署材料版本。 通过尝试手动调整语法/API漏洞,避免对代码的可读性产生不利影响. 这就是工具!

转录和多填充是两种非常有效的技术,可以弥补使用语言中最新稳定特性的代码与一个网站或应用程序需要继续支持的旧环境之间的差距。 由于JS不会停止改善,差距永远不会消失. 这两种技术都应作为联合来文项目今后每个生产链的标准组成部分。

## 解释里有什么?

由JS撰写的代码一个长期争论的问题:它是被解释的脚本还是编译的程序? 大多数意见似乎是,联合来文是一种解释性(描述性)语言。 但事实比这更复杂.

对于许多编程语言的历史来说,与编译的对应语言相比,"解释"语言和"描述"语言被贬低为低等. 这种曲折的原因很多,包括认为缺乏性能优化,以及不喜欢某些语言特征,如脚本语言一般使用动态打字而不是"更成熟"的静态打字语言.

被视为"编译的"语言通常会产生程序的一种可移植(二进制)的表示,在以后分发执行. 由于我们并不真正遵守JS的这种模式(我们分发源代码,而不是二进制形式),许多说法将JS从类别中贬低. 在现实中,一个程序“可执行”形式的分配模式在过去几十年里已经变得大不相同,也不太相关;对于眼下的问题来说,一个程序的形式传递到哪里已经不重要了。

这些错误知情的主张和批评,应当搁置. 清楚了解联合来文的解释或汇编是否重要的真正原因是如何处理错误的性质。

历史上,脚本或口译语言一般以自上而下和逐行的方式执行;在执行开始前通常没有通过程序处理的初始通道(见图1)。

那么,"parsed"语言与"编译"语言有什么共同点? 首先,所有编译的语言都被解析. 因此,一个解析的语言 是一个相当的方式 走向被编译。 在经典汇编理论中,解析后剩下的最后一步是代码生成:产生可执行的形式.

一旦任何源程序被完全解析,非常常见的是,其后续执行会以某种形式或方式包括程序解析形式的翻译——通常称为抽象语法树(AST)——到该可执行形式.

换句话说,解析语言在执行前通常也会执行代码生成,所以说,从精神上讲,它们都是编译语言,不是那么长的篇幅.

JS源代码在执行前被解析. 规格要求同样多,因为它要求在代码开始执行前报告"早期错误"——在代码中按统计确定的错误,如重复的参数名称. 没有解析代码,这些错误就无法识别。

因此,**JS是一个解析语言**,但它是*编译的*?

答案更接近于是而不是否。 解析后的JS被转换为优化的(二进制)形式,"代码"随后被执行(图2);在完成解析的所有艰苦工作后,引擎通常不会重新切换到逐行执行(如图1)模式——大多数语言/引擎不会,因为那样会效率很高.

具体来说,这个"汇编"产生一个二进制字节代码(of sorts),然后交给"JS虚拟机"执行. 有些人喜欢说这个VM是"解释"字节代码. 但是,这意味着Java, 和十几种其他JVM驱动的语言, 为此, 被解释而不是编译。 当然,这与Java/etc是编译语言的典型说法相矛盾.

有趣的是,虽然Java和JavaScript是非常不同的语言,但是解释/编译的问题在它们之间却相当紧密地联系在一起!

另一种皱纹是JS引擎可以在生成的代码(后剖析)上使用多段JIT(Just-In-Time)处理/优化的通行证,这同样可以根据视角合理标注"汇编"或"解释". 这其实是JS引擎引擎的引擎盖下 一个极其复杂的局面

2. JS引擎将代码解析为AST.

3. 然后,引擎将AST转换成一类字节代码,即二进制中间代表(IR),然后通过优化JIT编译器进一步精炼/转换.

4. 最后,联合核查团执行该方案。

### 网络大会(WASM)

促使联署材料大量演变的一个主要关切是业绩,即联署材料的解析/编译速度以及编译的守则的执行速度。

2013年,来自Mozilla Firefox的工程师演示了一个从C到JS的不真实3游戏引擎的端口. 这个代码在浏览器JS引擎在完全60fps性能上运行的能力是基于一套JS引擎可以具体实现的优化,因为JS版本的不真实引擎的代码使用一种倾向于JS语言子集的代码风格,命名为"ASM.js".

这个子集是JS有效的写法,在正常编码中有些不寻常,但是它向引擎发出某些重要的打字信息信号,使其能进行密钥优化. 采用ASM.js是解决联合来文运行时间业绩压力的一种方式。

但需要注意的是,ASM.js从未打算成为由开发者编写的代码,而是从另一种语言(如C)中转写了一个程序的代表,这些打字的"注释"是用工具自动插入的.

在ASM.js证明了工具创建的版本程序的有效性,这些版本可以由JS引擎更高效地处理之后,另一组工程师(最初也来自Mozilla)发布了Web Assem(WASM).

WASM与ASM.js相似,因为其最初的意图是提供一条路径,让非JS程序(C等)转换成一种可以在JS引擎中运行的形式. 与ASM.js不同的是,WASM选择在程序执行之前,通过完全不同于JS的形式代表程序,在JS解析/汇编中进一步克服一些固有的拖延。

WASM是一种更类似于大会(因此其名称)的代表格式,可以通过JS引擎跳过一般JS引擎的解析/汇编处理. 一个WASM目标程序的解析/编译在时间(AOT)之前进行;分发的是一个二进制包程序,准备让JS引擎以极少的处理方式执行.

WASM最初的动机显然是潜在的性能改进. 尽管这仍然是一个重点,但WASM的动机是希望在网络平台上实现非JS语言的更多平等。 例如,如果像Go这样的语言支持线性编程,但JS(语言)不支持,WASM提供了将这样的Go程序转换为JS引擎能够理解的形式的潜力,而不需要JS语言本身的线性特征.

换句话说,WASM减轻了在JS中添加功能的压力,这些功能大多/完全用于其他语言的转写程序. 这意味着JS的特征发展可以(通过TC39)判断,而不会因为其他语言生态系统的利益/需求而扭曲,同时让这些语言有一条通向网络的可行道路。

对WASM的另一种观点正在出现,有趣的是,甚至与网络(W)没有直接关系. WASM正在演化,成为一种跨平台虚拟机(VM)类型,其中程序可以编译一次,并在不同的系统环境中运行.

因此,WASM不仅仅是网络,WASM也不是JS. 具有讽刺意味的是,尽管WASM运行在JS引擎中,但JS语言是最不适合使用WASM程序源语言之一,因为WASM严重依赖静态打字信息. 即使是TypeScript(TS)——绝对是JS+静态类型——也不太适合(目前)转写到WASM,尽管AssemblyScript等语言变体试图弥合JS/TS和WASM之间的差距.

这本书不是关于WASM的,所以我不会花更多的时间讨论它,只为了提出最后一点. * 有些人建议WASSM指出, 他们常常对JS感到不快, 因为WASM让其他语言在JS引擎中运行,

但让我简单地说,WASM不会取代JS. WASM大大增加了网络(包括联署材料)所能完成的工作. 这是一件伟大的事情, 完全正统地说, 有些人是否会用它 作为逃生舱门 不得不写JS。

2009年,随着ES5的发布,JS增加了“限制性模式”作为鼓励改进JS方案的一种选择机制。

严格模式的好处远大于成本,但旧习惯死硬,现存(aka"legacy")代码基础的惯性确实难以改变. 所以不幸的是,十多年后,严格模式的*可选性*意味着它仍然不一定是JS程序员的默认.

为什么是严格模式? 严格模式不应被认为是对无法做的事情的一种限制,而应作为最佳行事方式的指南,使JS引擎拥有优化和高效运行代码的最佳机会. 大部分JS代码都是由开发团队研究,所以严格模式的*限制性*性(加上像linters!)往往通过避免一些在非限制性模式中滑动的更棘手的错误来帮助在代码上的合作.

最严格的模式控制形式是*早期错误*,意思是错误并非严格意义上的语法错误,但在编译时间(代码运行前)仍然抛出. 例如,严格模式不允许将相同的两个函数参数命名,并导致早期错误. 一些其他严格的模式控制只在运行时才被观察到,例如如何`this`默认为`undefined`而不是全局对象。

最好的想法是, 严格模式就像提醒你JS*应该如何写作, 如果你觉得自己被铐住了, 试图绕着严格的模式工作, 那应该是一个响亮的红色警示旗, 你需要重新思考整个方法。

每个文件上切换带有特殊 pragma 的严格模式( 除了评论/ 白空格外, 不允许在它之前 ):

```js
// only whitespace and comments are allowed
// before the use-strict pragma
"use strict";
// the rest of the file runs in strict mode
```

| 警报: |
| :--- |
| 值得注意的是 即使是流浪汉`;`在严格模式的pragma前出现, 只会使pragma无用; 没有出现错误, |

严格模式也可以被打开每个功能范围,对其周边环境的规则完全相同:

```js
function someOperations() {
    // whitespace and comments are fine here
    "use strict";

    // all this code will run in strict mode
}
```

有趣的是,如果一个文件有严格的模式打开,那么功能级的严格模式便不能使用. 故须拣一一.

**仅** 使用每个功能法对严格模式的有效理由是,当您正在转换一个现有的非限制性模式程序文件时,并且需要随着时间的流逝而少许改变. 否则,简单地为整个文件/程序打开严格模式就更好了.

许多人在想,JS是否会一度将严格的模式作为默认? 答案是,几乎肯定不是。 正如我们早些时候围绕反向兼容性展开的讨论,如果JS引擎更新开始假设代码是严格的模式,即使没有这样标记,这个代码也可能由于严格的模式控制而破裂.

然而,有一些因素可以减轻这种严格模式的不违约"不准确性"的未来影响.

对于一个,几乎所有的转录代码都以严格的模式结束,即使原始的源代码不是这样写的. 制作中的大多数联署文件代码被转录,这意味着大多数联署文件已经遵循严格的模式。 有可能推翻这个假设,但你确实必须走出你的方式这样做,所以极不可能.

此外,正在向使用ES6模块格式编写更多/大多数新的JS代码转变。 ES6模块假设严格模式,因此此类文件中的所有代码都会自动默认为严格模式.

结合起来,严格模式基本上是事实上的默认,尽管技术上它实际上不是默认.

## 定义

联合来文是执行ECMAScript标准(截至本文的ES-2019版),该标准由TC39委员会指导,由ECMA主办。 它在浏览器和其他JS环境中运行,如Node.js.

JS是一种多参数语言,意思是语法和能力允许开发者从各种主要范式,如程序、面向对象(OO/类)和功能(FP)中混合和匹配(以及弯曲和重塑!)概念.

JS是一种编译语言,意思是工具(包括JS引擎)过程,并在程序执行前核实一个程序(报告任何错误!).

用我们的语言来定义, 让我们开始了解它的进退两难。
